## 一、风险定义与判定标准

### 1.2 判定标准（合规红线）

下列任一项触发即判定为高风险：

1. 文档中出现 **身份证号、银行卡号（含 CVV/有效期）、手机号、邮箱、护照号、社保/医保号、人脸/指纹等生物特征、未公开的健康医疗信息、未公开的行踪轨迹** 等敏感字段，**未做脱敏**。
2. 文档中包含 **授权条款过度**（如"不可撤销、永久、全球性授权本公司用于任何用途"），违反《个保法》第 14 条（自愿、明确、合理）原则。
3. 合同/制度中 **未约定数据处理协议（DPA）必备条款**（目的、方式、安全措施、违约责任、删除返还），违反《个保法》第 21 条。
4. 涉及 **敏感个人信息处理、对外提供、公开、跨境传输** 场景，未取得"单独同意"，违反《个保法》第 23、25、29、39 条。
5. 数据出境未走 **安全评估 / 标准合同 / 认证** 任一合法路径，违反《个保法》第 38 条、《数据出境安全评估办法》。
6. 涉及 **未成年人（14 周岁以下）** 信息处理，未取得监护人同意，违反《个保法》第 31 条。
7. **隐私政策** 缺失必备告知项（收集目的/方式/范围、保存期限、权利救济、联系方式），违反《个保法》第 17、23、24 条。
8. 发生数据安全事件，**未在 24 小时内通知** 监管部门和受影响个人，违反《个保法》第 57 条、《数安法》第 29 条。

### 2.2 校验算法实现参考（Python）

```python
import re


def validate_id_card(id_str: str) -> bool:
    """GB 11643-1999 身份证校验位验证"""
    if len(id_str) != 18:
        return False
    weights = [7, 9, 10, 5, 8, 4, 2, 1, 6, 3, 7, 9, 10, 5, 8, 4, 2]
    check_codes = "10X98765432"
    try:
        s = sum(int(id_str[i]) * weights[i] for i in range(17))
        return check_codes[s % 11] == id_str[17].upper()
    except Exception:
        return False


def luhn_check(num_str: str) -> bool:
    """银行卡 Luhn 校验（ISO/IEC 7812-1）"""
    digits = [int(d) for d in num_str if d.isdigit()]
    if len(digits) < 13:
        return False
    digits = digits[::-1]
    total = 0
    for i, d in enumerate(digits):
        if i % 2 == 1:
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10 == 0
```

> **冲突说明**：身份证号（18 位数字 + 末位 X）与银行卡号（19 位数字为主）的正则有重叠；扫描引擎应优先匹配身份证规则后再做银行卡正则。

#### ⚠️ 勘误：统一社会信用代码规则（原始草稿有误，已修正并实测）

本知识库在复核阶段发现原规则**两处实质性错误**，若下游模型直接照抄将永远匹配不到任何真实代码：

| 错误 | 原写法 | 问题 | 修正 |
|------|--------|------|------|
| **① 长度错误** | 前缀 2 位 + `{17}` = **19 位** | 统一社会信用代码固定 **18 位**（GB 32100-2015）。该正则对任何真实代码都无法匹配 | 改为整体 `{18}` |
| **② 语义错误** | 前缀枚举 `11\|12\|...\|65\|71\|81\|82\|91` | 这是**省级行政区划代码**，被误当成了首 2 位。实际第 1 位是「登记管理部门代码」（1机构编制/5民政/9市场监管/Y其他），第 2 位是「机构类别代码」；行政区划码在**第 3–8 位** | 去掉错误枚举，改用全字符集 + 校验算法过滤 |

**为什么改用「宽正则 + 强校验」而不是「窄正则」**：统一社会信用代码与 18 位身份证号字符形态高度重叠，靠正则无法可靠区分。实测证明校验算法才是有效判别手段：

```
输入：91330100799655058B（真实企业代码）、11010519491231002X（身份证号）、91110108551385082Q（真实企业代码）
仅正则匹配        → 3 个全部命中（身份证号被误报）
正则 + GB32100校验 → 2 个命中，身份证号被正确排除 ✅
```

```python
# GB 32100-2015 统一社会信用代码校验（本库已实测通过）
CS = "0123456789ABCDEFGHJKLMNPQRTUWXY"  # 31 字符，剔除 I O S V Z
W = [1, 3, 9, 27, 19, 26, 16, 17, 20, 29, 25, 13, 8, 24, 10, 30, 28]


def uscc_ok(s: str) -> bool:
    if len(s) != 18 or any(c not in CS for c in s):
        return False
    m = 31 - (sum(CS.index(s[i]) * W[i] for i in range(17)) % 31)
    return (CS[0] if m == 31 else CS[m]) == s[17]


# uscc_ok('91330100799655058B') -> True
# uscc_ok('11010519491231002X') -> False  （身份证号被排除）
```

> **性质提醒**：统一社会信用代码是**组织机构**标识，不属于《个保法》定义的「个人信息」。但**个体工商户**的统一社会信用代码（第 1–2 位为 `92`）与经营者自然人身份强关联，此情形下应按个人信息对待。原表将其一律标为"一般个人信息"并不准确。

#### ⚠️ 其他已知误报（复核实测）

| 规则 | 误报情形 | 缓解建议 |
|------|----------|----------|
| IPv4 | 版本号 `1.2.3.4`、日期 `2024.1.1.1` 会被匹配 | 要求上下文出现 `IP\|地址\|服务器\|访问\|登录` 等关键词，或排除紧邻 `版本\|version\|v` 的匹配 |
| 银行卡号 | 长数字串（订单号、合同编号）被匹配 | **必须**接 Luhn 校验；实测 `6222021234567890123` 这类臆造号会被 Luhn 正确拦下 |
| 社保/公积金号 `\d{17,20}` | 极高误报，任何 17–20 位数字均命中 | 仅在字段名附近（`社保\|公积金\|参保`）启用，不可全文扫描 |
| 姓名（汉语） | 普通词组被匹配 | 仅在签字栏、名单表格、`联系人/负责人/法定代表人` 等字段附近启用 |

**给下游模型的使用纪律**：本表所有「有校验算法」的字段，**正则命中不等于命中 PII**，必须过校验后才可判定；无校验算法的字段（姓名、地址、社保号）必须依赖上下文，禁止全文裸跑，否则误报率会高到无法使用。

|---|---|---|---|---|---|
| **D1** | 未区分个人信息处理者/受托处理者角色 | 《个保法》第 21 条 | 协议中"双方"代称，未明确谁是处理者、谁是受托人；出现"乙方收集用户信息" | 明确"甲方为个人信息处理者，乙方为受托处理者"；以"处理者—受托处理者"模式区分 | 高 |
| **D2** | 委托处理未签 DPA 或 DPA 必备条款缺失 | 《个保法》第 21 条 | 合同中仅有"乙方应妥善保管甲方数据" | 应包含：委托目的、期限、处理方式、安全措施、违约责任、删除/返还、双方联系人、再委托限制 | 高 |
| **D3** | 单独同意场景遗漏（敏感个人信息） | 《个保法》第 23、29 条 | "涉及您个人信息的，我们将一并收集并使用" | 处理敏感个人信息应取得"单独同意"，并以弹窗/勾选方式实现 | 极高 |
| **D4** | 单独同意场景遗漏（对外提供/公开） | 《个保法》第 23、25 条 | "我们可能与合作伙伴共享您的信息" | 对外提供个人信息须单独取得同意；公开须取得"单独"且"明示"同意 | 极高 |
| **D5** | 单独同意场景遗漏（跨境） | 《个保法》第 39 条 | "我们会将您的信息存储于境外服务器" | 跨境提供须取得单独同意，并完成安评/标准合同/认证 | 极高 |
| **D6** | 授权条款过度 | 《个保法》第 14 条 | "用户授权本公司将信息用于任何商业用途" / "本授权不可撤销、永久、全球性" | 授权必须"自愿、明确、合理"，限定具体目的与方式；保留撤销权 | 高 |
| **D7** | 数据所有权/使用权归属约定不明 | 《个保法》第 4、44 条 | "数据归公司所有，用户不再主张任何权利" | 个人信息权益属于自然人；公司仅享有"处理权"；明确"处理者与数据主体的关系" | 高 |
| **D8** | 数据删除/返还义务缺失 | 《个保法》第 47 条 | "合同终止后，乙方有权继续保留数据" | 委托关系终止时，受托方应返还或删除数据并提供删除证明 | 高 |
| **D9** | 超期留存 | 《个保法》第 19 条 | "我们可能长期保存您的个人信息" | 应明确保存期限（最短必要）；到期删除或匿名化 | 中 |
| **D10** | 再委托（次级受托方）未经同意 | 《个保法》第 21 条 | "乙方可自行委托第三方处理" | 未经处理者同意，不得转委托；如确需，应取得"单独同意"并另行评估 | 高 |
| **D11** | 安全事件通知义务与时限缺失 | 《个保法》第 57 条 | "发生安全事件时由双方协商解决" | 应当约定 24 小时内（敏感 PII 立即）通知，并配合调查 | 极高 |
| **D12** | 跨境传输合法性基础缺失 | 《个保法》第 38 条 | "数据存储于海外" 未声明走哪条路径 | 应声明走：①国家网信办安全评估；②省级网信办标准合同备案；③经认证机构认证 | 极高 |
| **D13** | 内部制度缺少分类分级 | GB/T 43697-2024；《数安法》第 21 条 | 内部数据未按"核心/重要/一般"分类 | 应建立数据资产清单，按行业、领域、敏感度分级，差异化保护 | 中 |
| **D14** | 最小必要原则未体现 | 《个保法》第 6 条 | "为提供服务，我们需要收集您的全部信息" | 逐项列明收集字段及对应业务功能；超出必要的一律不收集 | 高 |
| **D15** | 权限管理与日志审计缺失 | GB/T 22239-2019 等保 2.0 | 内控制度无访问权限分级、操作日志留存要求 | 应有权限审批流程、操作日志 6 个月以上留存、定期审计 | 中 |
| **D16** | 脱敏规范缺失 | 《个保法》第 51 条 | 直接列示原始身份证号、银行卡号、手机号 | 应有脱敏规则：保留前 N 末 M 位、敏感字段哈希、附件加密 | 极高 |
| **D17** | 数据出境内部审批缺失 | 《个保法》第 38、39 条 | 境外子公司直接拉取境内数据 | 应设数据出境内部审批流程与前置 PIA 评估 | 高 |
| **D18** | 未成年人信息无差别处理 | 《个保法》第 31 条；《未成年人网络保护条例》 | 直接服务未成年人的 App 未设监护人同意机制 | 14 岁以下须取得监护人同意；14-18 岁可单独同意但应告知 | 极高 |
| **D19** | 自动化决策未告知 | 《个保法》第 24 条 | "我们将基于您的信息自动做出决策" | 应告知自动化决策逻辑、可能结果、提供拒绝/说明的权利 | 高 |
| **D20** | 隐私政策缺失必备告知项 | 《个保法》第 17 条 | 隐私政策只写"我们重视您的隐私" | 须列明：处理者身份、联系方式、目的、方式、字段、保存期限、权利、救济渠道 | 极高 |

## 六、真实案例（10 例，按时间排序）

> 所有案例均来自已下载原文或公开权威报道，金额、案号、处罚依据经查证可核。如有出入，以官方公告为准。

### 案例 1：滴滴出行 80.26 亿罚款（2022.7.21，国家网信办）

- **时间**：2022 年 7 月 21 日
- **主体**：滴滴出行科技有限公司
- **违规事实**：违法收集用户个人信息（17 项个人信息、APP 过度索取权限、人脸识别验证强制）、违规获取用户相册截图、过度获取乘客人脸识别信息等 16 项违法事实。
- **处罚依据**：《网络安全法》《数据安全法》《个人信息保护法》
- **处罚结果**：罚款 **80.26 亿元**；董事长程维 100 万、总裁柳青 100 万个人罚款。
- **来源**：国家网信办公告（2022.7.21）；多家央媒报道。
- **可核 URL**：https://www.gov.cn/xinwen/2022-07/21/content_5701983.htm

### 案例 2：人脸识别第一案 — 郭兵诉杭州野生动物世界（2020.11.20 一审 / 2021.4.9 二审）

- **时间**：一审 2020.11.20；二审 2021.4.9
- **主体**：原告郭兵（浙大法学博士），被告杭州野生动物世界有限公司
- **违规事实**：原告办理年卡时采指纹入园，后被告单方改为"刷脸入园"，构成违约；超出收集目的收集人脸信息。
- **处罚依据**：《消费者权益保护法》第 29 条（个人信息保护规则）；《民法典》人格权编
- **判决结果**：二审维持原判：①动物园赔偿 **1038 元**；②**删除**郭兵指纹年卡提交的照片、面部特征信息及指纹识别信息；③驳回其他诉求。
- **法院核心**：生物识别信息属敏感个人信息，超出原告知情同意范围的处理构成违约。
- **来源**：央视网 https://news.cctv.com/2021/04/10/ARTIyIB4yLJPUV26Zz8IcIZ6210410.shtml

### 案例 3：Meta 12 亿欧元 GDPR 罚款（2023.5.22，爱尔兰 DPC）

- **时间**：2023 年 5 月 22 日
- **主体**：Meta Platforms Ireland Limited
- **违规事实**：自 2020 年欧盟法院 Schrems II 判决后，仍持续将欧盟 Facebook 用户数据传输至美国服务器，未采取充分补救措施（如加密、假名化），违反 GDPR 第 46 条（跨境传输充分性保障）。
- **处罚依据**：GDPR 第 46 条跨境传输条款
- **处罚结果**：罚款 **12 亿欧元**（约 13 亿美元）；5 个月内停止跨境传输；6 个月内暂停新传输。
- **来源**：爱尔兰数据保护委员会公告 https://www.dataprotection.ie/en/news-media/press-releases/DPC-announces-1.2-billion-euro-fine-of-Meta
- **意义**：GDPR 史上最大单笔罚款之一。

### 案例 4：亚马逊 7.46 亿欧元 GDPR 罚款（2021.7.16，卢森堡 CNPD）

- **时间**：2021 年 7 月 16 日
- **主体**：Amazon Europe Core S.à r.l.
- **违规事实**：广告投放行为中收集处理用户个人信息未取得充分法律依据，违反 GDPR 透明度原则与合法性原则。
- **处罚依据**：GDPR 第 6 条（合法性）、第 12 条（透明度）
- **处罚结果**：罚款 **7.46 亿欧元**（约 8.87 亿美元）
- **来源**：CNPD 公告；多份国际媒体报道。

### 案例 5：江苏省消保委诉百度个人信息保护公益诉讼（2017.12—2018.3）

- **时间**：起诉 2017.12.11；立案 2018.1.2；撤诉 2018.3.12

- **处理结果**：百度整改到位后撤诉；属**全国首例**个人信息安全消费民事公益诉讼。
- **来源**：荔枝网 http://v.jstv.com/a/20180315/1521083933627.shtml

## 七、内部制度合规要点（机构层面）

> 不针对单一文档，而是机构"内部数据安全制度"应涵盖的最小集：

1. **数据分类分级制度**：依据 GB/T 43697-2024，将数据分为**核心/重要/一般**三级（一般数据再分敏感/常规）；建立数据资产清单。
2. **个人信息保护影响评估（PIA）**：依据 GB/T 39335-2020 与《个保法》第 55 条，在涉及敏感个人信息处理、自动化决策、委托处理、向境外提供等场景前进行 PIA，报告保存 ≥ 3 年。
3. **最小必要原则**：每项业务功能对应字段清单，年度审查；超范围字段强制下线。
4. **权限管理**：基于 RBAC/ABAC 的访问控制；特权账号双因素；季度权限复核。
5. **日志审计**：所有个人信息操作 6 个月以上留存；异常行为触发告警；年度审计报告。
6. **脱敏规范**：身份证保留前 6 后 4；银行卡保留前 6 后 4；手机号中间 4 位 `*`；邮箱前缀 `*`；姓名 1 字 `张*`、2 字 `张*`、3 字 `张*李`。
7. **加密标准**：静态 AES-256、传输 TLS 1.2+；密钥 KMS 管理。
8. **数据出境内部审批**：业务部门发起 → 数据保护官审查 → 法务/合规审查 → 主管领导批准；落地前完成安评/标准合同备案/认证。
9. **应急响应预案**：明确 24 小时内报告监管与受影响个人；演练每年 ≥ 1 次。
10. **供应商管理**：所有接触个人信息的供应商必须签 DPA；年度安全评估；黑名单机制。
11. **员工培训**：新员工入岗培训 + 年度复训；签署保密协议与竞业限制。
12. **离职交接**：离职前交还所有数据权限、删除本地数据副本、变更共享文档所有权。

## 八、对外公告 / 隐私政策合规要点

### 8.1 隐私政策必备内容（《个保法》第 17 条）

1. 处理者身份（公司全称、住所、联系方式）
2. 数据保护负责人姓名与联系方式
3. **每一项**个人信息字段的收集目的、方式、范围
4. 处理目的变更时通知方式
5. 保存期限（最短必要）
6. 委托处理、共同处理、对外提供清单
7. 跨境传输路径与备案情况
8. 自然人权利：查询、复制、更正、删除、撤回同意、注销账号、获得解释
9. 自动化决策的逻辑说明与拒绝权
10. 安全事件应急处置与通知
11. 未成年人特别保护机制
12. 投诉、举报渠道（监管 + 公司）
13. 争议解决方式与适用法律

### 8.2 单独同意触发场景（《个保法》第 23、25、29、39 条）

下列任一情况须"单独取得明示同意"，不能"一揽子"打包：

1. 处理**敏感个人信息**
2. 出于**对外提供/共享/转让**目的
3. **公开**个人信息
4. **跨境**传输
5. 自动化决策用于对个人权益有重大影响的场景
6. 其他可能对个人权益有重大影响的处理活动

### 8.3 文档公告常见失误（招标/采购/公示类）

1. **评委名单泄露手机号、身份证号**——应匿名化或脱敏
2. **联系人手机号写在正文**——应留专用客服电话或邮箱
3. **投标人法人身份证扫描件**——应遮挡
4. **附件 PDF 元数据含作者姓名**——应清除后再上传
5. **图片 EXIF 包含 GPS**——应去除 EXIF
6. **签字栏模板连带个人签名图片**——应替换为电子签
7. **批量盖章/扫描导出文件名含个人信息**——应改为编号
