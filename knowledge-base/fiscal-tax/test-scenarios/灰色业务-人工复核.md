# 灰色业务人工复核测试用例（5 个剧本）

> **用途**：验证 EAIDE 审核专家系统在**模糊地带**业务场景下，期望触发**规则不全覆盖 → 人工复核**而非自动通过或自动拒绝。
>
> **预期结果**：`score 50-89`、合规规则部分命中（可能 conflict）、`needs_hitl=True` 但不是 critical、需要**专家判断**（人或 LLM）给最终判定。

---

## 场景 G1 · 真实业务的"挂靠经营"

### 业务背景
- 公司：可G1建筑工程公司
- 申请人：项目经理（ID：`pm-016`）
- 业务类型：**挂靠在某建筑公司名下承接项目**
- 金额：项目造价 **¥8,000,000** + 对外开具专票
- 三流：货物流**真实存在** + 资金流**部分回流**（实际施工方与被挂靠方之间的结算）

### 凭证材料（**部分不清晰**）

| 编号 | 类型 | 完整度 |
|---|---|---|
| E01 | 与被挂靠方协议 | ✅ |
| E02 | 实际项目施工合同（与业主） | ✅ |
| E03 | 资金流转凭证 | ⚠ 部分回流 |
| E04 | 货物 / 服务实际交付 | ✅ |
| E05 | 发票链路 | ✅（被挂靠方开具） |

### 自动识别要素

| ID | 触发 | 风险等级 |
|---|---|---|
| V-LAW-006 | 三流**部分**一致 + 资金回流（**难判**） | warning |
| A-法律模糊 | 挂靠经营是否构成虚开（**最高法 2025.11 案例 B**：有真实业务 + 三流一致不构成虚开） | 灰区 |

### 法规点
- 最高法 2025.11 案例 B：挂靠经营**有真实交易 + 三流一致** → 不构成虚开
- 但需保证：实际业务真实 + 无骗税故意

### 自动决策（**灰区 - 不阻断**）

```
规则系统冲突：基础设施 V-LAW-006 警示 + 案例 B 例外
   ↓
系统无法自动判定，需要 LLM 介入
   ↓
needs_hitl=True（升级到**税务专家 LLM** + **人工复核**）
   ↓
规则不全 → 不评分，自动转人工
```

## 场景 G3 · 劳务报酬 vs 工资薪金边界

### 业务背景
- 公司：可G3科技公司
- 申请人：HR 总监（ID：`hr-018`）
- 业务类型：**外部技术专家劳务报酬支付**
- 金额：向独立顾问（**有正式雇佣关系 + 又独立承揽项目**）支付顾问费 **¥200,000**（按月）

### 自动识别要素

| ID | 触发 | 风险 |
|---|---|---|
| I03 | **劳务报酬未代扣 / 误判为工资** | warning |
| I-LAW | **劳务报酬 vs 工资**边界灰区 | 灰区 |

### 法规点
- 个税法：劳务报酬 vs 工资薪金 → 不同税率 + 不同预扣
- 实施条例：界定标准
  - **工资**：**任职受雇**关系 → 单位直接用工 + 受单位制度约束
  - **劳务**：**独立**提供劳务 + 不存在雇佣关系

### 灰区识别

| 维度 | 工资 | 劳务报酬 |
|---|---|---|
| 雇佣关系 | 存在 | **不存在** |
| 受单位制度约束 | 是 | 否 |
| 工作时间 | 单位安排 | 自主安排 |
| 支付周期 | 固定月薪 | 按次 / 不定期 |
| 福利（社保等） | 通常有 | 通常无 |
| 经营风险 | 由单位承担 | 自负 |

### 期望决策

```
自动识别：工资 vs 劳务报酬 灰区
   ↓
LLM 介入：基于合同 + 工作模式 + 支付模式判定
   ↓
needs_hitl=True
```

## 场景 G4 · 关联方利益输送 vs 商业实质

### 业务背景
- 公司：可G4 集团有限公司（**上市公司**）
- 申请人：CFO（ID：`cfo-019`）
- 业务类型：**向控股股东全资子公司采购"咨询服务"**
- 金额：**¥30,000,000**（**占公司同类支出 80%**）
- 定价：按服务成本 + 20%（**高于第三方报价**）

### 自动识别要素

| ID | 触发 | 风险 |
|---|---|---|
| V-LAW-014 | 关联交易金额异常偏高 | warning |
| F-LAW-018 | 关联交易**商业实质不清** | 灰区 |
| R-LAW-006 | 关联交易定价显著偏离独立交易原则 | **violation** |
| C-LAW | 上市公司关联交易披露要求 | warning |

### 法规点
- 证券法 + 上市公司信息披露管理办法（关联交易披露）
- 关联交易决策程序（独立董事 + 董事会 + 股东会）
- **独立交易原则**的实质判定
- **商业实质**：是否存在真实服务 + 实际功能 + 经济实质

### 灰区识别

| 视角 | 倾向 |
|---|---|
| **控股股东视角** | 利益输送嫌疑 |
| **上市公司视角** | 商业安排合理 |
| **独立董事视角** | 价格公允存疑 |
| **审计师视角** | 重大错报风险 |

## 场景 G5 · 业务招待费边界

### 业务背景
- 公司：可G5 制造公司
- 申请人：销售经理（ID：`sm-020`）
- 业务类型：**业务招待 vs 员工福利边界**
- 金额：**¥150,000**
- 凭证：餐饮发票 + 客户名单（**部分名单为内部员工**）

### 灰区识别

| 分类 | 边界 |
|---|---|
| **业务招待** | 用于**外部客户**的交际应酬 + 有客户参与 |
| **员工福利** | 用于**内部员工**的福利（节日 / 团建 / 聚餐） |
| **会议费** | 用于**公司会议的外部餐饮**（需会议通知 + 议程 + 签到） |

### 自动识别要素

| ID | 触发 | 风险 |
|---|---|---|
| D04（业务招待费） | 超过限额（营业收入 5‰ 与发生额 60% 孰低） | **violation** |
| D-LAW | **业务招待 vs 员工福利 vs 会议费**边界灰区 | 灰区 |
| F-LAW | 凭证不清晰区分 | warning |

### 法规点
- 所得税法实施条例第 41 条（业务招待费）
- 业务招待费按**发生额 60%**扣除，**且不超过营业收入 5‰**
- 员工福利按工资总额 **14%** 扣除

## 总体测试策略

### 单元测试套件

```python
# services/agent/tests/test_fiscal_gray_scenarios.py

import pytest
from agent.audit_expert import submit_audit_task

GRAY_SCENARIOS = [
    # (scenario_id, status_in, score_low, score_high, requires_more_info, llm_required)
    ("G1", ["pending_human_review", "requires_more_info"], 50, 80, False, True),
    ("G2", ["pending_more_info", "pending_human_review"], 60, 85, True, False),
    ("G3", ["pending_classification"], 50, 80, False, True),
    ("G4", ["pending_audit_committee"], 30, 80, False, True),
    ("G5", ["pending_categorization"], 40, 80, False, True),
]


@pytest.mark.parametrize(
    "scenario_id,status_options,score_low,score_high,more_info_required,llm_required",
    GRAY_SCENARIOS,
)
def test_gray_scenario_subject_to_judgement(
    scenario_id, status_options, score_low, score_high, more_info_required, llm_required
):
    """验证灰色场景走人工复核（不是自动通过也不是自动拒绝）"""
    task = load_fixture(f"fiscal-tax/test-scenarios/灰色业务-人工复核.md#{scenario_id}")
    result = submit_audit_task(task)

    # 灰区既不应该自动通过，也不应该自动拒绝
    assert result["status"] in status_options
    assert result["needs_hitl"] is True
    assert score_low <= result["score"] <= score_high  # 在中间区间

    # 不应当自动 approve
    assert result["status"] != "approved"
    # 不应当自动 blocked（除非 V3 这种）
    assert result["status"] not in ["blocked"]

    if llm_required:
        assert result.get("llm_analysis") is not None or result.get("reviewer_required") is not None

    if more_info_required:
        assert result.get("request_to_user") is not None

    # 必须有审计日志
    assert result["audit_log"]["sha256_evidence_hash"] is not None
```

## 灰区处理的关键原则

### 原则 1 · **疑罪从无**
- 不阻断、但需要人工介入
- **不放过**：必须升级审批 + 留痕
- **不误杀**：不要自动拒绝合规业务

### 原则 2 · **规则 vs LLM**
- **规则明确 → 自动决策**
- **规则冲突或缺失 → LLM 辅助**
- **业务实质判定 → 人工 + LLM**

### 原则 3 · **可解释性**
- 每个判定**必须留痕**
- 5 维评分 + 规则命中 + LLM 推理过程 + 人工决策记录
- 完整 SHA-256 签名链

### 原则 4 · **审计可回放**
- 决策树全部可回放
- 每次升级都有决策者 + 时间 + 原因

### 原则 5 · **学习闭环**
- 每次人工决策都要回流到**规则库 / LLM 训练集**
- 业务负责人可发起"规则升级"流程
- EAIDE 系统应当**持续学习**灰区判定

---

**核心结论**：灰区处理是 EAIDE 审核专家系统**最关键的能力** —— 既不能误杀（让合规业务人员无法工作），又不能放过（让违规业务蒙混过关）。**G1-G5 的判定准确性直接决定系统的可信度**。
